## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Stage 1 of the delivery plan in docs/production-architecture.md. The site needs a server runtime before any owner editing is possible, because TASK-009 requires server-enforced authorization and a static export cannot provide it. This stage builds that runtime and proves the release procedure against a throwaway hostname, without touching the live site. Proxy host 9 must keep serving koreokorp.com from koreokorp-web for the whole of this stage; the rehearsal happens on a separate staging proxy host. The prototype remains the visual and behavioural source of truth, so the port must match mockups/koreokorp-v2/index.html rather than reinterpret it.
<!-- SECTION:DESCRIPTION:END -->

Four defects were found and fixed during this slice, each caught by running the procedure rather than trusting it. (2) The deploy script recorded the rollback target from an OCI revision label the Dockerfile never set, so previous-release-app was always empty and the rollback target was undeterminable; it now reads the running container's image before replacing it, and the image carries a standard revision label. (4) Staging initially served none of the live site's security headers, because proxy_set_header at server level is overridden by the location-level directives Proxy Manager emits; headers-more is the correct mechanism. Two API quirks are recorded in docs/vps-deployment.md so they are not rediscovered: the API rejects the extra fields its own UI sends (agree, ssl_forcesh), requires forward_scheme, and updates via the plural /nginx/proxy-hosts/:id route. tests/app/staging-tls.spec.js runs the same assertions against public staging over trusted TLS and passes 2/2 with KOREOKORP_STAGING=1, and is skipped otherwise so the rest of the suite does not depend on the staging host.
